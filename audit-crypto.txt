KRITIS

1. falcon.rs — SeedRng tidak domain-separated per level, keystream Falcon-512 dan Falcon-1024 dari seed yang sama saling overlap

rust
fn refill(&mut self) {
    let mut hash = Sha3_256::new();
    hash.update(b"XPARQ Falcon-512 deterministic keygen v1");  // hardcoded, tidak peduli level
    hash.update(self.seed);
    hash.update(self.counter.to_le_bytes());
    ...
}

SeedRng::new(seed) tidak menerima level sama sekali, dan domain tag-nya hardcode "Falcon-512" walau dipakai juga untuk Level5 (keypair_from_seed(FalconLevel::Level5, seed) → SeedRng::new(*seed)). Konsekuensinya: derive Falcon-512 dan Falcon-1024 dari seed yang identik menghasilkan prefix keystream yang identik pula — RNG stream Falcon-1024 dimulai dari byte yang sama persis dengan yang dipakai Falcon-512, cuma dikonsumsi lebih banyak. Ini bukan RNG independen, ini RNG yang linked secara struktural antar dua key generation.

Kenapa ini serius: dokumentasi function-nya sendiri bilang "Deterministically derives a Falcon keypair for mnemonic and bearer-key recovery" — jelas dipakai buat skenario HD-derivation di mana satu seed bisa dipakai untuk lebih dari satu skema (persis kasus di profile.rs yang saya flag sebelumnya soal seed reuse lintas algoritma). Gaussian/NTRU trapdoor sampling di Falcon keygen sangat sensitif terhadap kualitas & independensi randomness; shared-prefix keystream antara dua keygen dari input berkorelasi berpotensi membocorkan hubungan struktural antar dua secret key.

Fix: tambahkan level: FalconLevel ke struct SeedRng, masukkan ke domain tag di refill() (misal encode level.logn() ke hash), dan pastikan keypair_from_seed meneruskan level itu ke SeedRng::new(level, seed).

TINGGI

2. argon2.rs — argon2id_pow_hash_with_memory tidak validasi memory.blocks.len() vs memory_kib
PoWMemory dibuat terpisah dari pemanggilan hash (biar reusable), tapi tidak ada assert bahwa buffer yang di-pass cocok ukurannya dengan memory_kib yang dipakai di Params::new(memory_kib, ...) pada call itu. Kalau caller salah pairing (reuse PoWMemory yang dialokasikan untuk memory_kib A, dipanggil dengan parameter memory_kib B), tergantung implementasi argon2 crate — bisa panic atau baca/tulis buffer yang salah ukuran. Tambahkan check eksplisit:

rust
if memory.blocks.len() != memory_kib as usize {
    return Err(CryptoError::InvalidPoWParameters);
}

atau lebih baik, hapus parameter memory_kib dari fungsi ini dan derive dari memory.blocks.len() langsung — satu sumber kebenaran, konsisten dengan gaya kalian yang anti redundant.

3. error.rs — pesan InvalidSignatureEncoding hardcode "ML-DSA-44" padahal ada 5 skema

rust
CryptoError::InvalidSignatureEncoding => {
    #[cfg(feature = "sqisign-blockchain-test")]
    return f.write_str("signature bytes are not valid SQIsign Level 5 encoding");
    #[cfg(not(feature = "sqisign-blockchain-test"))]
    f.write_str("signature bytes are not valid ML-DSA-44 encoding")
}

Ini jelas sisa dari desain lama single-scheme, sebelum agility ke 5 skema (MLDSA44/65/87 + Falcon512/1024). Salah/menyesatkan untuk debugging kalau errornya sebenarnya dari Falcon-1024. Juga sqisign-blockchain-test feature merujuk skema (SQIsign) yang tidak ada di codebase manapun yang saya lihat — dead cfg branch dari eksperimen yang sudah ditinggalkan. Ganti jadi pesan generik ("signature bytes are not valid for the specified account type") dan hapus cfg SQIsign kalau memang sudah tidak dipakai.

4. Kebingungan penamaan modul: profile.rs isinya crypto-agility, padahal lib.rs sudah punya agility.rs terpisah

rust
pub mod agility;
...
pub mod profile;
...
pub use agility::*;
pub use profile::*;

profile.rs yang saya audit isinya Signature enum + activation_height() + PublicKey/AccountSignature/SigningSeed — itu literally definisi "crypto agility" (dukungan multi-skema dengan height-gated activation). Tapi nama modulnya "profile", sementara ada modul agility terpisah yang tidak saya lihat isinya. Apakah ini dua mekanisme agility yang tumpang tindih, atau profile.rs salah nama dan harusnya isinya digabung ke agility.rs? Ini exact jenis redundant-abstraction yang biasanya kalian hindari — worth diklarifikasi sebelum saya kasih rekomendasi lanjut, soalnya kalau agility.rs juga define sesuatu yang serupa, salah satu harus dihapus.

MEDIUM

5. address.rs — hashing manual tanpa lewat domain_hash/HashDomain
address_from_key_material dan address_checksum pakai Sha3_256::new() + concat manual dengan domain string lokal (b"XPARQ signature address", ADDRESS_CHECKSUM_DOMAIN), padahal hash.rs sudah punya infra domain_hash(HashDomain, bytes) dengan length-prefixing yang konsisten. Kebetulan aman di sini (field variable-length-nya selalu di posisi terakhir, jadi tidak ambigu tanpa length prefix), tapi inkonsistensi ini bikin pattern hashing tersebar di dua tempat berbeda. Tambahkan HashDomain::Address dan HashDomain::AddressChecksum, pakai domain_hash di sana juga — satu jalur hashing domain-separated buat seluruh crate.

6. falcon.rs — hasil .keygen(...) di generate_keypair_with_rng tidak dicek

rust
match level {
    FalconLevel::Level1 => KeyPairGenerator512::default().keygen(level.logn(), rng, &mut secret, &mut public),
    FalconLevel::Level5 => KeyPairGenerator1024::default().keygen(level.logn(), rng, &mut secret, &mut public),
}
Ok(FalconKeyPair { ... })

Return value dari keygen() dibuang. Memang ada safety net di belakang (FalconPublicKey::from_bytes/FalconSecretKey::from_bytes validasi ulang via decode), jadi kegagalan tetap tertangkap — tapi implisit dan gampang kebobolan kalau ada yang refactor tanpa sadar itu satu-satunya jaring pengaman. Tambahin komentar eksplisit, atau cek return value langsung kalau fn_dsa expose-nya.

7. FalconSignature::from_bytes cuma cek panjang, tidak structural-validate seperti public/secret key
valid_public_key/valid_secret_key ada, tapi tidak ada valid_signature. Kalau fn_dsa's verify() bisa panic pada bytes yang panjangnya pas tapi encoding-nya rusak, itu DoS vector di consensus path (validator crash saat verifikasi tx dari attacker). Perlu dikonfirmasi ke fn_dsa punya spec — kalau verify() cuma return bool/error dengan aman untuk garbage input berukuran benar, tidak masalah.

MINOR / nit

Konvensi branding tidak konsisten dengan yang saya tahu soal Aegis Network: file ini pakai SHA3-256 di mana-mana ("XPARQ" domain tags), sementara arsitektur Aegis yang kita bahas sebelumnya pakai SHA3-512. Ini bikin saya curiga file-file ini sebenarnya punya XPQ (varian Go yang berjalan paralel), bukan Aegis — atau ada rename yang belum tuntas. Tolong konfirmasi supaya saran saya tetap relevan ke codebase yang benar.
HashDomain::Emission => b"XPARQ_HASH_Emission" — satu-satunya tag yang mixed-case, sisanya all-caps. Kosmetik, tapi tanda kemungkinan copy-paste.
address_from_public_key: Vec::with_capacity(32 + ...) tapi prefix aktual cuma 24+1=25 byte — capacity hint sedikit meleset, tidak berbahaya, cuma realokasi kecil.
FalconError tidak impl Display/Error seperti CryptoError — inkonsistensi pola error-handling antar modul.
