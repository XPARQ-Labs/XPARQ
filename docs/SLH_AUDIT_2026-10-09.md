# Shared SHAKE / SLH-DSA internal review — 2026-10-09

Scope: the local RustCrypto SLH-DSA dependency changes, shared SHAKE backend,
XPARQ signing wrapper, signature account authorization and wallet entropy.
This is a review by the implementing agent, not an independent cryptographic
audit, NIST module validation, or a complete node security assessment.

## Result

No algorithm change or ownership bypass was identified in the examined patch.
Pure SHAKE 128s/192s/256s remain FIPS 205 parameter sets; replacing a SHAKE256
implementation with a byte-compatible SHAKE256 implementation does not create
a new signature construction. Passing sampled vectors does not prove security
or establish validated-module status.

Two hardening findings were identified during the initial review. That review
added tests/docs; subsequent [hardening](HARDENING_2026-10-09.md) guards the
identified secret buffers and defaults all new wallets to 24 words.
Explicit 12-word creation/recovery remains supported by user choice; its entropy
limit still applies. Neither follow-up establishes an independent audit.

## Findings from the initial review

### A1 — Medium, conditional: wallet entropy can undercut the selected parameter strength

`wallet/src/lib.rs`, `generate_bip39_mnemonic` and
`account_wallet_from_bip39_mnemonic`, accept 12-word / 128-bit entropy for all
schemes. The new-wallet CLI defaults SLH wallets to 24 words, but accepts an
explicit `--words 12`; existing wallet tests also exercise this combination.
Expanding 128 bits into a longer seed cannot provide 192 or 256 bits of seed
entropy. This limits resistance to seed search; it does not imply that a
128-bit wallet can presently be stolen.

Recommendation: require 24 words for newly created 192s/256s wallets and explain
the entropy limit when restoring older 12-word wallets. Preserve recovery of
existing identities. This is an existing integration limitation, not a
regression caused by sharing SHAKE.

### A2 — Medium, conditional: secret intermediate wiping is incomplete

The XPARQ master seed and expansion buffer, prepared SLH signing-key fields,
and shared SHAKE state have explicit zeroization on drop. However, upstream
`wots.rs` (`wots_pk_gen`, `wots_sign`) and `fors.rs` (`fors_node`) create secret
PRF outputs in ordinary `Array` locals without explicit wiping. `SkSeed` and
`SkPrf` wrappers also have no independent zeroizing destructor; the enclosing
signing key wipes its owned fields.

A process-memory disclosure or crash dump may expose residual material.
No remote spend exploit was demonstrated. FORS secrets deliberately published
in a signature are not treated as a leak here. This behavior is inherited from
upstream and remains after the patch.

Recommendation: review and wipe unpublished secret intermediate buffers, then
repeat compatibility tests. Rust moves, registers and compiler copies mean
explicit wiping still cannot guarantee erasure of every historical copy.
Avoid formatting upstream `SigningKey` with Debug: it derives Debug including
secret fields. XPARQ's `SigningSeed` uses redacted Debug.

## Source comparison

Upstream: RustCrypto `slh-dsa 0.2.0-rc.5`, commit
`58bae19939c244ec4ef83bf16235b41b5b9c3c83`.
Downloaded crate SHA-256:
`371c02fe34044d8866ddf7cb0e8204a87ef31a39f0408bed41c4253ea9dd61ed`.
Workspace baseline HEAD: `d500f2a7e4d438be16cba2096686ebe43bcb4a54`;
this review concerns the uncommitted SLH implementation on that baseline.

Compared all Rust source files against the extracted upstream crate. Production
SHAKE hashing changes only its imported implementation. Other source changes
gate SHA2 imports, exports, compressed addresses, size implementations and
test expansions behind a feature. WOTS, FORS, hypertree signing/verification,
SHAKE address encoding and parameter constants retain upstream logic.
See [patch provenance](../depend/slhdsa/slh-dsa/XPARQ_PATCHES.md).

The shared backend uses SHAKE domain padding `0x1f`, not SHA3 padding, with
rates 168/136 for SHAKE128/256. Streaming absorption/squeezing, reset and cloning
were reviewed and tested at rate boundaries. Keccak backend choice depends on
public platform capabilities. This is not a formal side-channel analysis.

Default crypto dependencies contain one shared Keccak package, protocol SHA3
and shared SHAKE; they contain no SHA2/HMAC. The optional benchmark feature
does not register additional signature account identifiers. Other workspace
components may independently depend on SHA2/HMAC.

The signature policy still derives identity from the public key and salt,
compares it with the owner program instance, then verifies the transaction
commitment. Account scheme identifiers and parsing limits were not changed by
the dependency patch.

## Added validation

- Three complete deterministic external Pure signing known answers from NIST
  ACVP: SHAKE128s tcId 215, SHAKE192s tcId 237, SHAKE256s tcId 256. All use empty
  context. Public key and full signature bytes must match; changing context
  must fail verification. `.sk` fixtures are public NIST test keys.
- SHAKE128/256 fixtures independently generated with Python `hashlib`: 22
  input cases, including empty input, exact rate boundaries and 4096 bytes,
  with 513 output bytes each. Seven chunk sizes exercise fragmented update,
  fragmented read, empty calls, cloning, reset and finalize-with-reset.
- Existing official keygen and positive/negative external verification vectors,
  and pre-refactor public-key/signature-digest fixtures cover all three active
  SLH schemes. Provenance is in the [vector README](../crypto/tests/vectors/slhdsa/README.md).

Reproduction:

Results: default release run **37 passed, 1 ignored** (the existing manual
benchmark); optional SHA2-feature audit run **4 passed**. All three added signing
cases matched complete official signature bytes. No failed tests.

## Limits and deployment considerations

SLH wallet seed expansion is XPARQ's domain-separated derivation, not a claim of
a NIST-validated key generation module. The underlying signature algorithm is
specified by [FIPS 205](https://csrc.nist.gov/pubs/fips/205/final).
Shared SHAKE reduces dependency duplication but creates a common implementation
failure surface for ML-DSA and SLH-DSA; they are not independent implementations
of their hash primitives.

Excluded: formal proof, exhaustive ACVP testing, independent review, hardware
side channels, complete dependency advisory analysis, network denial of service,
and full VM/ledger validation. Existing kernel end-to-end SLH spend tests passed
before this test-only review; they were not rerun here. The open findings should
be addressed before claiming complete secret erasure or full-strength high-level
wallet entropy.
