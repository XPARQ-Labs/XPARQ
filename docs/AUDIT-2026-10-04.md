## Findings

Seven findings: two high-severity availability issues under the conditions
explained below, and five medium-severity issues. No theft of funds or signature
forgery was confirmed within this review's scope. This report does not certify
the security of the entire system.

## A-01 — Slow requests can exhaust RPC connection slots

Locations: [rpc.rs:87](../runtime/src/node/rpc.rs#L87),
[rpc.rs:389](../runtime/src/node/rpc.rs#L389),
[mod.rs:43](../runtime/src/node/mod.rs#L43).

The 10-second read timeout bounds an individual read waiting for data, rather
than the entire request. The parser reads headers and bodies in loops without
an absolute deadline or minimum transfer rate. A sender delivering small amounts
of data before each timeout can retain a slot far longer than 10 seconds.
Header and body sizes are bounded, but request duration can still be very long.

RPC accepts eight active connections, with at most four per IP. Two IP addresses
that can reach RPC can occupy every slot while slow requests continue; other
clients receive 503 responses. The default loopback binding reduces exposure.
Remote risk applies when RPC is exposed or proxied without a total request
deadline.

Remediation: enforce absolute deadlines for header and body phases, calculate
the remaining time before each read, and require a minimum transfer rate.
Rejection responses in the accept loop also need a write timeout. Test a client
that trickles data past the total deadline while each read receives data before
the idle timeout. This attack has not been tested against a running node.

## A-02 — Large deployments are rejected before reaching the handler

Locations: [rpc.rs:434](../runtime/src/node/rpc.rs#L434),
[mod.rs:40](../runtime/src/node/mod.rs#L40),
[deploy.rs:7](../kernel/src/program/deploy.rs#L7).

Every request passes through a parser enforcing a 256 KiB Content-Length limit,
including /program/deploy and /program/deploy/quote. The kernel permits bytecode
up to 1 MiB and operations up to 2 MiB. The quote handler's 2 MiB check cannot
help requests already rejected by the parser.

Impact: the wallet and RPC cannot deploy envelopes larger than 256 KiB even when
their structure is accepted by the kernel. Envelopes also contain payment data,
a public key, and a signature, so the effective bytecode limit is smaller.
This is a transport mismatch, not a claim that every 1 MiB program can execute
within the fuel ceiling.

Remediation: apply endpoint-specific body limits after parsing the route while
preserving the ordinary transaction limit. Test valid deployment envelopes above
256 KiB and rejection above the operation limit. The reproducer uses the original
XPVM validator and parser: a valid 270,023-byte program requires 54,002 fuel
(below the 65,536 ceiling), but a declared Content-Length equal to its code size
is rejected by the quote parser before the body is read.

## A-03 — Wallet pagination can keep appending pages with the same cursor

Location: [rpc.rs:10](../wallet/src/native/rpc.rs#L10).

fetch_account requests additional pages while next_utxo_cursor is present;
only empty pages are rejected. A faulty or malicious RPC server can return
nonempty pages with a repeated or cyclic cursor. The wallet keeps extending
its UTXO list.

The 1 MiB limit per response does not bound the total number of pages or UTXOs.
Impact includes looping, memory growth, and possible wallet OOM. This requires
the wallet to use that RPC server or receive modified responses; it is not
evidence of private key disclosure.

Remediation: reject previously seen cursors, verify cursor progress, deduplicate
share IDs, and bound aggregate pages, UTXOs, bytes, and operation duration.
The reproducer uses the original function: five pages with the same cursor are
accepted, and only a deliberate stub error on the sixth call stops the loop.

## A-04 — Wallet RPC can hang without a time limit

Locations: [rpc.rs:29](../wallet/src/native/rpc.rs#L29),
[rpc.rs:38](../wallet/src/native/rpc.rs#L38),
[rpc.rs:92](../wallet/src/native/rpc.rs#L92).

GET and POST use TcpStream::connect without an explicit connection timeout,
read timeout, or write timeout. Response reading waits for EOF rather than
stopping when Content-Length is satisfied. An RPC server keeping the socket
open, including after sending complete JSON, can hang a wallet command.

Remediation: add connection, read, and write timeouts and a total deadline.
Use bounded response framing that stops after the complete body is received.
Test servers that send no response and those that send a complete response but
keep the socket open. This is distinct from pagination: one response is enough
to hang the command.

## A-05 — Deployment quote cost scales with the entire registry

Locations: [rpc.rs:117](../runtime/src/node/rpc.rs#L117),
[deploy.rs:102](../kernel/src/consensus/deploy.rs#L102),
[registry.rs:97](../kernel/src/program/registry.rs#L97).

Quoting clones the registry, including all bytecode, serializes it before
insertion, and serializes it again afterward to calculate state growth.
Insertion also scans the entire registry for the owner/nonce pair.

The quote endpoint intentionally accepts drafts before authorization verification
and does not verify input balances. A small structurally valid request can
trigger work proportional to the entire registry without paying a fee.
Eight concurrent requests can amplify CPU and RAM usage. The impact grows
with the chain; large-load benchmarking has not been performed.

Remediation: calculate the exact canonical encoding delta for one record and
the map prefix without cloning or serializing the entire registry. Index
owner/nonce pairs and limit quote concurrency and request rates. Test burn
calculation equivalence against serialization across different map sizes.

## A-06 — Synchronization accumulates all block bodies in memory

Locations: [chain_sync.rs:177](../runtime/src/node/chain_sync.rs#L177),
[chain_sync.rs:201](../runtime/src/node/chain_sync.rs#L201),
[mod.rs:69](../runtime/src/node/mod.rs#L69).

Header synchronization allows 100,000 headers per session. synchronize_blocks
holds all bodies in a Vec before calling apply_verified_branch, with no
aggregate byte budget. Each block can be up to 2 MiB: the theoretical limit
for one session approaches 195 GiB of serialized data, excluding decoded
objects and staging clones.

Catching up to a large valid chain or fork can exhaust RAM. Peers must still
provide valid PoW headers and matching bodies; this finding does not assume
that PoW or Merkle roots can be forged. The 195 GiB figure is a theoretical
bound, not a benchmark result.

Remediation: enforce a session byte budget and use staging storage or bounded
batches while preserving reorganization atomicity and rollback. Test large
catch-up operations while measuring peak RSS.

## A-07 — Chain identity fixtures fail

Locations: [mod.rs:210](../kernel/src/genesis/mod.rs#L210),
[phase4_vectors.rs:433](../kernel/src/ledger/phase4_vectors.rs#L433),
[consolidation_compatibility.rs:16](../kernel/tests/consolidation_compatibility.rs#L16).

Three tests fail:

- bounded_work_rules_have_frozen_mainnet_chain_spec_identity
- frozen_phase4_vectors_match_execution
- mainnet_genesis_and_chain_spec_match_the_current_structure

Actual hash: 413c21227db374780f677b818771b0d2718459a6bba5f35abd2a0bc2b219ac33.
Fixture: d09a338588ea581ccaed1ee4bd798c258ea2a9d488033621a2aa5af83cac6b8c.

This determinism and compatibility gate remains open, as already acknowledged
in the repository documentation. Fixture failures alone do not prove a fork
between nodes running the same revision. Handshakes compare chain-spec hashes
and reject different identities.

Remediation: establish the intended protocol identity, audit rule changes,
decide whether a reset or migration is needed, and then reconcile the fixtures.
Do not merely replace the expected hash to make the tests pass.

## Verification and scope limits

The review covers authorization, coin and asset conservation, staged ledger
state, rollback and reorganization, the VM registry, RPC/P2P framing, the mempool,
storage and snapshots, and the wallet. Positive controls observed include
signatures binding calls, payments, and genesis; ledger-based input ownership
checks; checked monetary arithmetic; and mutations using staged state.
Passing tests provide evidence but do not replace fuzzing or comprehensive proofs.

- Formatting check: passed, with warnings about nightly-only options on stable.
- Clippy workspace/all-targets/offline: passed with warnings.
- Workspace/offline/no-fail-fast tests inside the sandbox: failed; three chain
  fixtures failed, and the sandbox denied socket operations in several tests.
- Five connection_tests outside the sandbox: all passed.
- Workspace tests outside the sandbox: only the three A-07 fixtures failed,
  across two kernel targets. All 48 node unit tests, seven network E2E tests,
  eight snapshot/storage tests, and active wallet tests passed. Network E2E
  completed in 579.30 seconds, including the three-node Program lifecycle with
  gossip, mining, restart, reorganization to a stronger fork, and removal of
  orphan transaction indexes.
- Two normally ignored wallet lifecycle tests were explicitly run outside the
  sandbox: both passed (205.62 seconds), covering assets and XPQ spending and
  consolidation.
- Parser and pagination reproducers: both passed.

Reproducer: [audit/reproduce.py](audit/reproduce.py), run with python3.
It uses original production functions with stubs, without networking, real
wallets, or deployment. It is not an end-to-end exploit test.

The output summary is saved in [audit/verification.txt](audit/verification.txt).
Full session logs: /tmp/xparq-audit-*.log. This audit does not cover every
vendored dependency, mathematical cryptographic analysis, online dependency
advisories, production configuration, long-running fuzzing, or public network
lifecycles. Staking is not implemented; there is no staking contract to audit
at this revision.

Priorities: address A-01 and A-06 for availability, followed by A-02 through A-05.
Reconcile A-07 before declaring the mainnet release gate passed.
