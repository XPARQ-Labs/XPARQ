# Code audit — 9 October 2026

An initial review of the local code, focusing on RPC resource limits, wallet
account reads, transaction admission, and testing controls. This is not a
comprehensive audit of cryptographic primitives, all vendored dependencies,
or all consensus rules. No production code was changed. The findings below
come from code inspection; network exploits have not been reproduced end to end.

## 1. P2 — Unpaginated asset shares can block wallet operations

Locations: `runtime/src/node/explorer.rs:112–129`,
`wallet/src/native/rpc.rs:48–49`.

The account endpoint includes all asset shares owned by the account in every
response, even though coin UTXOs are paginated. The wallet limits the entire
response to 1 MiB. A JSON simulation with 7,000 shares, 64-character hexadecimal
IDs and asset identifiers, and an amount of `1` produced 1,134,018 bytes for
the asset_shares field alone.

Accounts with enough shares cannot be read through fetch_account, which also
breaks transaction input selection, deployment, and UTXO tracking. Senders can
choose asset recipients, so accumulation does not necessarily result from the
account owner's actions. The cost and feasibility of a dust attack have not
been measured.

Remediation: separate or paginate asset shares so that coin read responses do
not depend on the size of the asset inventory. Test large accounts through
the wallet client.

### Implementation follow-up

The wallet coin-read dependency is addressed by `GET /program/coins/{program_id}`.
This endpoint shares coin pagination, reservation flags, and snapshot generation
with the legacy account response, but never enumerates or serializes asset shares
or asset balance aggregates. Wallet input selection, deployment funding, and UTXO
tracking now use it for every page. Upgrade the node before the wallet.

The legacy `/program/account/{program_id}` response retains its asset fields for
compatibility. Asset pagination and the other findings below remain separate work.

Validation: a detached-state regression with 7,000 asset shares across 7,000 assets
and 1,001 coin UTXOs confirms that coin responses are identical to those without
assets, remain below the wallet response limit, and paginate correctly. HTTP tests
cover the new route, legacy account compatibility, and invalid pagination queries.
The wallet pagination test checks use of the new route on every page. All 12 wallet
binary unit tests and the four focused node coin tests passed. Clippy completed
with existing warnings.

## 2. P2 — RPC timeouts do not bound total request duration

Locations: `runtime/src/node/rpc.rs:87–92, 483–492`,
`runtime/src/node/mod.rs:44–47`.

The 10-second read timeout applies to socket operations, while the request
read loop has no overall deadline. A client that sends small amounts of data
before each timeout can hold a slot for a very long time. There are only
8 global slots and 4 per IP; two IP addresses can occupy all slots if the RPC
is accessible. RPC binds to loopback by default, so remote impact depends on
the exposure configuration.

Remediation: enforce absolute header/body deadlines and a total request time
limit; set the remaining timeout from the deadline before each read.

## 3. P2 — Wallet pagination ignores snapshot changes

Locations: `wallet/src/native/rpc.rs:10–24`,
`wallet/src/native/mod.rs:51–57`.

The node provides utxo_snapshot, but the wallet stores it as _utxo_snapshot
and directly combines pages. If blocks or the mempool change between
requests, the result mixes different states: spent or reserved inputs may
still be selected, or new UTXOs preceding the cursor may be missed.
Transactions may consequently be rejected, or available funds may be treated
as insufficient. This does not demonstrate a consensus violation or loss
of funds.

Remediation: compare snapshots across pages and restart reads with a bounded
retry count when they change; also consider next_height consistency.

## 4. P2 — Repeated cursors cause an endless loop and memory growth

Location: `wallet/src/native/rpc.rs:13–23`.

The wallet only rejects empty pages. A node that repeatedly returns nonempty
pages with the same next_utxo_cursor keeps the loop running and appends
duplicate UTXOs to the Vec. The 1 MiB limit per response does not bound the
accumulated data across all pages.

Remediation: validate cursor progress, UTXO ordering and uniqueness, and an
overall read budget; add a regression case for repeated cursors.

## 5. P2 — The wallet RPC client can wait indefinitely

Locations: `wallet/src/native/rpc.rs:32–45, 95–103`.

GET and POST do not configure connect/read/write timeouts. Reads wait for
EOF instead of stopping once the Content-Length body is complete. A node
that accepts a connection and then stays silent, or sends a response without
closing the connection, can hang wallet commands.

Remediation: add connection timeouts and request deadlines, plus HTTP framing
parsing that bounds headers and bodies and stops once the response is complete.
